# 网络小说共创

一个让多人共同创作网络小说的产品设想。小说借鉴 Git 的提交历史：作品默认有 `main` 主线，作者也可以从已有章节节点创建分支，发展不同的故事路线。每章对应一个节点，提交和修订均可追溯。

项目计划覆盖浏览器和手机，使用 GitHub 账号登录，并以作品创建者自己的 GitHub 私有仓库作为云存储。成员可以在不同时间上线、读取和提交更新。开发者提供应用，不集中托管用户作品，也不维护作品存储服务器。

## 当前进度

仓库已实现阶段一的本地可用版本：用原生 HTML/CSS/JavaScript 跑通作品创建、章节阅读与续写、故事分支、修订历史与对比、本地草稿和作品导出。数据保存在当前浏览器的 `localStorage`，刷新后可以继续使用。

当前使用明确标注的本地演示身份，尚未接入 GitHub 登录、私有仓库、真实成员邀请、可信权限执行或跨设备同步。以下产品目标和云端方案仍是后续实施方向，不代表已经上线。

| 页面 | 现有用途 |
| --- | --- |
| `start.html` | 产品入口，可前往工作台或创建作品 |
| `main.html` | 本地作品工作台 |
| `new.html` | 创建作品，填写标题、简介和共创规则 |
| `read.html` | 阅读章节、切换故事线、创建分支、查看修订差异、导出作品 |
| `creat.html` | 续写或修订章节，自动保存和恢复本地草稿 |
| `signin.html` | 本地演示身份与 GitHub 接入状态说明 |
| `style.css` | 桌面与手机共用样式 |
| `app.js` | 页面渲染、交互与修订对比 |
| `store.js` | 本地持久化、章节版本与分支数据层 |

数据接口及本地实现边界见 [DATA_API.md](DATA_API.md)。初次打开会提供演示作品，也可以创建自己的作品。

## 产品目标

- 让用户创建作品，并设定简介、共创规则和参与方式。
- 让参与者沿 `main` 接续创作，也可以从已有章节节点创建分支，发展不同故事路线。
- 清晰展示作品的章节、作者、更新时间和版本关系。
- 让用户比较、阅读和追溯不同版本，避免协作内容互相覆盖；被删除的文字仍可在改动记录中查看，并以删除线标示。
- 在浏览器与手机上提供连贯体验，通过 GitHub 同步已提交作品；离线时继续阅读缓存和保存草稿。
- 作品仅通过邀请加入，不设公开投稿或公开加入入口。
- 成员角色与操作权限按本项目的规则定义；GitHub 提供账号身份和存储能力。

## 核心概念

- **作品**：包含标题、简介、共创规则、受邀成员与章节版本的创作空间。
- **章节节点**：一个章节对应一个节点，记录作者、正文和创建时间，并指向故事发展所依据的上一个节点。
- **分支**：从某个章节节点开始延伸的独立故事路线；不同分支可以有不同的后续章节。
- **`main` 主线**：作品默认展示的故事路线，也是新作品的初始分支。其他分支可以从 `main` 或已有分支的任一章节节点创建。
- **参与者**：通过邀请加入作品的用户，拥有创建者、协作者或读者等权限。具体角色规则待定。

版本历史与故事分支示意：

```text
作品
└── main
    └── 节点 A（第 1 章）
        └── 节点 B（第 2 章）
            ├── 节点 C（第 3 章，main）
            └── 分支路线 X
                └── 节点 D（另一种第 3 章）
                    └── 节点 E（第 4 章）
```

每章是一个节点，节点通过父节点连接成故事路线。修改已提交章节时，保留该章节的旧修订并产生新修订；不回写历史。编辑器中的未提交草稿可以另行保存。版本对比只比较同一章节的前后修订，采用类似 Git diff 的呈现方式：新增文字正常显示，删除的文字保留并加删除线标示；必要时提供开关，在干净阅读与改动审阅之间切换。删除线是修订差异的展示，不会把被删文字重新写入当前正文。

## 网络与身份方案

采用“本地优先 + GitHub 云存储”。作品数据分散保存在各创建者的仓库中，在线同步依赖 GitHub。协作者无需同时在线，也无需运行自己的 P2P 节点。

- **GitHub 登录**：用户通过 GitHub 授权登录；以 GitHub 用户 ID 关联项目身份，用户名和头像作为展示信息。登录后还需检查作品成员资格和项目权限。
- **用户持有仓库**：建议一部作品对应一个创建者持有的私有仓库。作品管理页关联该仓库，开发者不提供统一的作品存储账号。
- **异步协作**：甲上传章节或修订后可以离线；乙之后从 GitHub 读取更新并继续写作。
- **本地草稿**：编辑时自动保存到本地，正式提交时写入仓库。应用区分本地已保存、待同步、已同步和冲突状态。
- **存储接口**：通过 GitHub API 读取文件、创建提交和更新分支；不要求浏览器安装 Git。GitHub 提供相应的 [Git 数据库 API](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-your-git-database)。
- **并发提交**：提交前读取目标分支最新状态；远端已更新时先同步并处理冲突，避免强制覆盖他人的修改。分支更新使用非强制方式，参见 [Git 引用更新接口](https://docs.github.com/en/rest/git/refs#update-a-reference)。
- **可用性**：网络中断、授权失效或 API 限流时保留本地草稿，恢复后重试；提供作品导出能力。

### 登录接入边界

优先评估 GitHub App，以便按仓库授予应用访问权限。用户授权后的实际 API 权限仍受 GitHub 用户权限和应用权限共同限制，参见 [GitHub App 用户令牌说明](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)。

浏览器和手机端的授权回调、令牌交换与刷新需要在接入阶段确认。目前 GitHub 文档中的 Web 授权码交换要求 `client_secret`，因此不能提前承诺仅靠静态页面完成全部登录流程。若采用保管应用密钥的轻量托管授权组件，应单独确认其部署和维护范围；它不承担作品存储。应用密钥与用户令牌不写入作品仓库。参见 [GitHub OAuth 授权流程](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)。

### 作品与 Git 的映射

- 一部作品对应一个仓库，`main` 是默认故事线，其他故事线对应仓库分支。
- 一个章节对应一个稳定的章节节点 ID 和正文文件，例如 `chapters/<chapter-id>.md`；作品元数据记录章节顺序与父节点关系。
- 一次正式新增或改写形成 Git 提交。章节节点与提交分别表示章节身份和版本变化，同一章节可以有多次修订。
- 章节标题、正文和顺序等关联变更应放入同一次提交，保持读取到的数据一致。
- 改写已被多条故事线引用的章节时，修改只作用于当前分支；其他分支保留原有版本。
- 删除线由应用比较同一章节的不同修订后渲染，不把删除线标记写进当前正文。

## 邀请制与权限

权限以本项目的作品、成员和操作为单位定义。下面的角色是初步设计，不直接对应 GitHub 仓库角色：

| 项目角色 | 初步权限 |
| --- | --- |
| 作品创建者 | 管理作品设置、成员邀请、角色分配和主线规则 |
| 作品管理员 | 在创建者授权范围内管理成员及协作流程 |
| 协作者 | 阅读作品，在获准范围内新增/修改章节和创建分支 |
| 读者 | 阅读获准内容及修订历史 |

- 加入作品需要项目邀请。邀请关联作品、受邀 GitHub 用户 ID 和项目角色；接受后形成作品成员记录。
- 登录成功、拥有仓库访问能力和拥有项目操作权限分别检查；应用根据项目角色展示并校验操作。
- 项目角色决定是否允许修改章节、创建分支、管理邀请或调整主线。GitHub 权限承担底层仓库访问约束，不自动决定用户在项目中的角色。
- 移除成员或降低权限时，需要同时处理项目授权和底层存储访问；已经下载的内容无法远程收回。

**权限实现约束：** 具有 GitHub 仓库写权限的成员可以直接调用 GitHub 修改文件，前端隐藏按钮或仓库中的普通角色配置不能单独强制执行项目权限。实现时需要选择可信的受控写入机制，或由客户端验证的授权/内容记录机制；后者也无法阻止有仓库权限的人删除或破坏远端数据。项目邀请与存储访问的衔接是 MVP 的必要设计项。

GitHub 个人私有仓库的协作者权限包含读写，不能直接授予只读协作者。因此，项目中的“读者”角色如何获得受限内容访问，需要在底层接入方案中解决。参见 [个人仓库权限说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository)。

## 目标平台与体验

### 浏览器

- 提供已创建/受邀作品列表、个人主页、作品详情、阅读、版本树和创作编辑器。
- 支持键盘写作、版本比较、较复杂的作品管理。
- 在桌面和窄屏浏览器中都能使用。

### 手机

- 优先适配阅读、续写、查看提交历史和协作动态等高频场景。
- 编辑器适配小屏输入、自动保存、草稿恢复和中断后继续写作。
- 导航、按钮和表单适合触屏操作，并考虑网络不稳定时的反馈。

移动端实现形式（响应式网页/PWA、跨平台应用或原生应用）尚未决定。确定之前，先让产品流程和数据接口保持平台无关。

## MVP 范围

首个可用版本建议聚焦一条完整共创流程：

1. 使用 GitHub 登录，加载个人主页和项目成员身份。
2. 创建作品、关联创建者持有的私有仓库，并填写标题、简介和共创规则。
3. 通过项目邀请加入作品，并按项目权限查看作品详情、`main` 和其他故事线。
4. 阅读章节，查看节点作者与提交时间。
5. 从任一已有章节节点接续创作或创建分支；每个章节作为节点保存。
6. 查看分支路线及章节历史；同一章节的修订对比中以删除线显示被删除文字。
7. 浏览器与手机使用同一 GitHub 账号，通过仓库异步同步已提交内容；离线草稿留在本地。
8. 执行项目角色规则，完成项目邀请与 GitHub 存储访问的衔接及权限变更处理。

评论、点赞、私信、内容推荐、实时多人同时编辑、版本合并、审核与举报流程可在验证核心共创体验后再规划。

## 初步数据模型

以下是产品概念，不是已实现的数据库结构：

- `User`：GitHub 用户 ID、用户名、显示名称、头像。
- `Novel`：标题、简介、规则、创建者用户 ID、GitHub 仓库 ID/地址、默认分支、创建时间。
- `Membership`：用户 ID、作品、项目角色、操作权限、成员状态；与 GitHub 仓库角色分别管理。
- `Invitation`：作品、受邀 GitHub 用户 ID、拟授予的项目角色、邀请者、有效期及接受/撤销状态。
- `Branch`：作品、Git 分支引用、起始章节节点、起始提交 SHA、当前头提交 SHA、创建者。
- `ChapterNode`：稳定章节 ID、父节点、标题、正文路径、作者、创建时间；章节顺序和修订内容随分支变化。
- `ChapterRevision`：章节 ID、所在分支、提交 SHA、正文快照、作者、提交说明和时间，可从 Git 历史读取。
- `Draft`：用户、作品、目标分支/章节、基准提交 SHA、未提交正文和更新时间；默认只存本地。
- `SyncState`：仓库、分支、本地已知提交 SHA、待同步修改和冲突状态。

需要在实现阶段进一步确定：项目权限的可信执行方式、GitHub 授权组件、仓库初始化和访问授予流程、从历史章节创建分支时的内容范围、分支合并规则，以及个人阅读进度和未提交草稿的跨设备同步方式。

## 本地运行

无需安装前端依赖或执行构建。推荐在项目目录启动静态服务器，让所有页面共享稳定的浏览器存储来源：

```powershell
python -m http.server 8000 --bind 127.0.0.1
```

随后打开 <http://127.0.0.1:8000/start.html>。也可以直接打开 `start.html`；浏览器对 `file://` 的存储隔离策略不同，如果跳转后数据不一致，请使用上述服务器方式。

体验路径：进入工作台 → 创建作品 → 写第一章 → 继续写下一章 → 回到某章创建分支 → 在分支续写或修订 → 查看该章修订历史与删除线对比。编辑时草稿保存到本机，刷新或重新进入同一编辑入口可恢复。

### 数据与版本边界

- 作品和草稿仅保存在当前浏览器、当前来源下；不同浏览器、设备、端口及 `file://` 与 HTTP 页面之间不共享数据。清除站点数据会移除本地作品，请通过作品导出保存备份。
- 从某章创建分支时，只继承截至该章的路线及当时修订。之后在任一故事线修改共享章节，都不会改写其他故事线的正文或历史。
- 正式提交会检查编辑时的分支版本，发现已落盘的其他更新则拒绝覆盖并保留输入。此原型使用 `localStorage`，并非具备事务能力的协作后端；极短时间内的多标签同时写入仍可能竞争，GitHub 阶段需要实现非强制分支更新及冲突处理。
- JSON 导出包含作品、分支、正文及修订历史；当前尚未提供导入恢复与云端备份。
- 当前不是 PWA，HTTP 页面没有离线安装或资源缓存承诺；已打开的页面可继续本地编辑，直接打开本地文件不需要网络。
